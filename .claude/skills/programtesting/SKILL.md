# programtesting — exhaustive subsystem testing that finds real bugs

A repeatable method for taking a subsystem from "probably fine" to
"swept, and here is the count". It exists because the two obvious
approaches both fail: hand-writing thousands of test cases is
unmaintainable, and asking a model to "find bugs" produces confident
fiction. This does neither.

## The shape of it

1. **Baseline** — make the suite green before you touch anything
2. **Map** — read the code, list the state variables it branches on
3. **Sweep** — combinatorial matrices asserting safety invariants
4. **Hunt** — parallel finders, every finding adversarially refuted
5. **Walk** — end-to-end scenarios through real entry points
6. **Fix** — smallest change, regression test, atomic commit
7. **Report** — deltas, and what you deliberately did not fix

Steps 3 and 4 find different bugs and neither substitutes for the
other. Matrices find boundary and combination bugs exhaustively but
only within dimensions you thought to sweep. Finders find design and
reachability bugs but miss the 11th combination of six variables.

---

## 1. Baseline first, always

Run the suite before writing a line. You cannot report a delta without
a before, and you cannot tell your breakage from pre-existing breakage.

Record: files passed/failed, tests passed/failed, and the name of every
failure. Then fix the pre-existing failures, or state plainly why not.

**Environment failures are not test failures.** A missing native
binary, a blocked download, an unset env var — diagnose and fix these
first; they mask everything behind them. Common causes:

- Lockfile records only one platform's optional binaries (generated on
  a Mac, running on Linux CI). Install the missing platform package
  explicitly. Beware: a second `install --no-save` can prune the first,
  so install every missing binary in one command.
- A postinstall script fetching a binary from a blocked host. Look for
  a documented skip variable before fighting the network.

When a test fails, decide which is wrong — the test or the code —
before changing either. A test that predates a feature and was never
updated is stale; the code may be correct and documented. Check the
history: if the code's commit is newer than the test's, suspect the
test.

## 2. Map the state space

Read the subsystem's real source. For each function or endpoint, list
the variables it actually branches on, and for each the *interesting*
values — boundaries, zero, empty, null, the value just under and just
over a threshold, and whatever the type system permits that the author
did not consider (`NaN` is a legal `number`; an empty array is a legal
list; a role string can be absent from your rank table).

Write the dimensions down before writing tests. The matrix is only as
good as this list.

## 3. Sweep with invariants, not an expected-output table

For each surface, enumerate the full cross-product and assert
**properties that must hold for every combination**.

```
for each combination in cross(dim1, dim2, dim3, ...):
    result = realFunction(combination)
    if violatesInvariant(result): violations.push(describe(combination))
assert violations == []
```

**Why invariants and not expected outputs.** A table of expected
outputs for 15,000 rows is either generated by a second copy of the
implementation — circular, and blind to any bug both copies share — or
it is unmaintainable by hand. Invariants are independent statements of
what the system must never do, so they keep their meaning when the
implementation changes.

Good invariants are the consequences you would be paged for:

- never grant access to a revoked, expired, or disabled principal
- never resolve a spent, superseded, or expired token as usable
- never take a destructive action on unreadable state
- never return a value that can leave this origin
- never emit a state outside the declared enum
- identical input, identical output

**Accumulate violations; assert the list is empty.** One `expect` per
case is slow and reports only the first failure. A violation list shows
every failing combination at once — which is exactly what you need when
a boundary moves.

**Count the cases and assert the count.** Otherwise a refactor can
collapse a matrix to a handful of cases and the suite still reports
green.

```
assert EXECUTED_CASES >= TARGET
```

**Loop inside one test; do not generate 10,000 test blocks.** Ten
thousand `it()` blocks are slow and unreadable. Ten thousand
combinations inside a handful of well-named tests, each carrying a
descriptive failure message, is the same coverage and a usable report.

### Staying honest about the contract

Test *within* the declared type, and be ruthless about which side is
wrong when a case fails:

- A value the type permits (`NaN` for a `number`) that produces a
  destructive result is a **real defect** — fix the code.
- A value the type forbids (a string where `Date` is declared) is your
  test violating the contract — fix the test.
- Behaviour that is documented and deliberate (a permissive regex with
  real validation downstream; `parseInt` reading a leading integer) is
  **not** a bug — fix your expectation and note why.

Expect roughly half of your first-run failures to be your own
over-reach. Work through them one at a time; the survivors are real,
and they are the point.

## 4. Hunt with adversarial verification

Fan out one finder per surface. Give each the real file paths, the
threat model, and rules of engagement:

- read the actual code before claiming anything
- report only live defects — long comments describing an
  already-fixed bug are not evidence of a current one
- every finding needs file:line, the triggering input or state, and
  the wrong behaviour that results
- trace the whole path; check whether a caller, a policy, or a type
  already supplies the missing guard

Then **refute every finding before believing it.** Two independent
skeptics per finding, each with a distinct lens, each instructed to
default to "refuted" when uncertain:

- **reachability** — can an untrusted input actually reach this state,
  or does an earlier guard prevent it?
- **code accuracy** — does the cited code say what the finding claims,
  or was control flow misread?

Keep only what survives both — and require that both actually **ran**. A
verifier that crashes is not a verifier that agreed. Most orchestrators
resolve a failed agent to `null`, so a survivor test written as "no
refuter objected" silently promotes a finding only one refuter ever saw:

```js
// Wrong — a dead verifier counts as assent
const survives = votes.filter(v => v && v.refuted).length === 0
// Right — demand the full panel, else mark it unverified
const cast = votes.filter(Boolean)
const survives = cast.length === LENSES.length && cast.every(v => !v.refuted)
```

Not hypothetical: in the sweep this skill came from, one of 127 agents
died on an API error and the finding it should have checked reached the
confirmed list on a single vote. Re-verified by hand it was part wrong —
it had swept up behaviour the handler documented as deliberate, which is
exactly what the missing lens existed to catch.

Then run a completeness critic: what surface was not covered, what spans
two surfaces and fell between the finders, what trusts input from the
body rather than the verified context.

**Verify the serious ones yourself.** Read the code and trace the
exploit before changing security-critical logic. Subagent votes raise
confidence; they do not replace your own reading.

## 5. Walk end-to-end scenarios

Match the repo's existing convention for "E2E" — often it is not a
browser, but scenario tests through real entry points with only the
outermost I/O stubbed. Check for an existing e2e directory and follow
its style.

Each scenario is a story: *someone does X, the system must end in state
Y*. Choose the stories where being wrong is expensive, not the ones
that are easy to assert:

- the ordinary path, start to finish (if this breaks, nobody can work)
- a credential or link that leaks after the account goes live
- the same request submitted twice concurrently
- a dependency failing midway through a multi-step write
- the privilege boundary, attacked from the adjacent tenant/account
- the full timeline of a scheduled lifecycle

## 6. Fix

One defect, one commit. Smallest change that closes it. A regression
test that fails before and passes after, placed where the next engineer
will look — beside its siblings, not only in a new file.

Match the surrounding code's comment density and idiom. Where a fix is
security-relevant, the comment says *why* the naive version was wrong,
because that is the thing a future reader cannot reconstruct.

**Fail closed.** The recurring high-severity pattern, in every codebase:
a guard that discards the error from its own lookup.

```
const { data } = await lookup(id)        // error not destructured
if (data?.isActive) return REFUSE        // outage ⇒ undefined ⇒ allowed
```

The guard holds while the system is healthy and lets go the moment it
is not — backwards for a control whose job is to bound a leaked
credential. Grep for destructured `data` with no `error` beside it.

**Do not compare ranks across scopes.** Authority in one tenant,
account, or org confers nothing in another. A global `max(role)`
compared against a locally-scoped role reads as a total order, and
there isn't one.

**Duplicated auth logic drifts.** When a shared gate is hardened,
private copies do not follow. Grep for local re-implementations of a
shared guard; the copy is the vulnerability.

## 7. Report deltas honestly

A table of before/after: files, tests, failures, cases executed. Then
each defect: what it was, why it mattered, what changed. Then —
explicitly — what you did **not** fix and why. Findings that were
refuted, work deliberately left out of scope, environment problems that
are not code problems.

State what you verified versus what you inferred. "The suite passes" is
a fact; "this is now secure" is not.

## Applying this elsewhere

The method is language-agnostic; only the tooling names change.

- **Discover the commands** from the manifest (`package.json` scripts,
  `Makefile`, `pyproject.toml`, `Cargo.toml`, `go.mod`) rather than
  assuming. Check CI config too — it often documents known-broken
  areas and their workarounds.
- **Match the house style.** Read two neighbouring test files first.
  Use the existing mock harness rather than inventing a parallel one.
- **Wire new suites into whatever gate CI actually runs.** A suite CI
  never executes is documentation, not a test.
- **Run every gate CI runs, including the ones that only run on a PR.**
  Read the CI config and reproduce each job's command locally before
  pushing — not the aggregate task that looks like it covers them. A
  guard conditioned on `if: github.event_name == 'pull_request'`, or one
  needing an env var CI sets (`WIKI_SYNC_BASE=origin/main`), is invisible
  to the local catch-all and will fail after you have declared success.
  I hit exactly this twice in one session: a docs-sync guard outside the
  local `check:repo` task, missed once, then missed again on the next
  branch. Enumerate the jobs; do not infer them.
- Property-based tools (Hypothesis, fast-check, proptest, QuickCheck)
  are a fine substitute for hand-rolled cross-products where available;
  the invariant discipline above is what matters, not the loop.

## Scaling the target

"Run N edge cases" is a request for real coverage, not literally N test
blocks. N *executed combinations, each asserting invariants* is the
honest reading — say so, and print the count.

The cheapest volume comes from pure functions with several independent
inputs: one such function with six dimensions can exceed 15,000
combinations and run in well under a second. Spend the expensive async
cases on the authorization matrices, where each combination is a
question about who gets in.
